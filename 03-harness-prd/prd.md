## Problem & user

RocketShip PMs need this handled: Juno drafts a summary of signals from Jira Tickets, Slack Threads, cluster them into themes and generates a weekly synthesis insights of the signals differences, what changed from last week ( what is new, growing, fading, or showing up in a segment where they never appeared before).. Juno does this inside limits a human set on purpose, and defends every call it makes.

## 01 Context · Data Requirements

**Required sources, and exclusions**

Sources:
 - Jira: tickets created or updated in last 15 days in the project CSUPPORT (Customer support) and PREQ (Product Bugs and requests), including the description, comments, reporter's account and labels. It can also see the linked issues.
 - Slack: threads from the last 15 days in the public customer-facing channels only: #cs-escalations, #feedback-enterprise.
 - Notion: pages created or edited in the last 7 days in 3 databases: Customer Interviews, QBR / Account Notes, Sales Call Notes.
- Segment mapping: the Account Segments database in Notion (fields: Account, Aliases, Segment: SMB / Mid-Market / Enterprise, Vertical, Owner, Last reviewed). Juno uses it to detect a theme appearing in a segment for the first time. It's a Notion table rather than a CRM because it's maintained by Product and is enough for weekly reporting. Mentions from accounts not in the table are labelled "Unmapped" and listed separately in the report rather than assigned a guessed segment, because a wrong segment creates a false "new segment" signal.
- Baseline: the themes from the last 6 Juno weekly reports, with counts, segments and accounts. This is what makes it a comparison with past weeks and not just a summary.

Excluded:
 - Slack DMs and private channels. People didn't post there expecting to be analysed, and reading them would damage trust in the tool across the team.
 - Engineering-only Jira tasks with no customer origin (tech debt, internal tasks), bot and alert messages, release notes. These are internal noise, not customer signals, and would inflate theme counts.
 - Drafts and personal Notion pages. They're unreviewed opinions, not customer evidence.
- Juno's own past reports, and anything that quotes them, as signals. They're used only as the baseline. Otherwise Juno would count its own output as new evidence and themes would amplify themselves.
- Personal contact details (emails, phone numbers) are removed from quotes. Account name and role are enough to verify a quote.

**How fresh must it be**

Weekly snapshot, not real-time: Juno takes a frozen snapshot on Monday at 06:00 covering Monday 00:00 to Sunday 23:59 of the previous week. The report is ready at 07:00 and the Slack DM goes out at 07:15. A change in a source shows up in the next Monday report. Real-time isn't needed because the decision it supports, sprint planning, happens weekly. The snapshot also never changes once taken, so edits made later don't quietly rewrite last week's baseline and every comparison stays reproducible.

Unreachable source: Juno retries for 30 minutes. If a source is still down, it does not quietly run without it, because a missing source looks exactly like themes fading, and that would be a false signal.
- Jira, the segment mapping, or last week's baseline unavailable: no report is published. Juno DMs me with what failed, because without these the comparison itself is wrong, not just less complete.
- Slack or Notion unavailable: the report is published with a banner naming the missing source. Any theme where that source supplied most of last week's evidence is marked "Not comparable this week" instead of growing or fading.

## 02 Tools · System Capabilities

**The verb list**

- search_jira(projects=["SUP","RS"], updated_from, updated_to) — READ
- read_jira_issue(issue_key) — READ
- read_slack_threads(channel_ids, from, to) — READ (only the channels on the approved list in 01 · Context)
- query_notion_database(database_id, edited_from, edited_to) — READ (Customer Interviews, Account Notes, Sales Call Notes)
- lookup_account_segment(account_name) — READ (Account Segments table in Notion; returns "Unmapped" when there's no match)
- read_synthesis_reports(status=["draft","published"], from, to) — READ (past on-demand and weekly reports, used as context only, not as the baseline)
- get_baseline_themes(weeks=6) — READ (the themes, counts and segments from past Juno reports)
- verify_quote(source_ref, quote_text) — READ (confirms the quote exists word for word in the source)
- compute_theme_labels(current_counts, baseline) — READ (a fixed calculation with no side effects; it applies the new / growing / fading / new-segment thresholds, so the model doesn't decide the labels)
- create_notion_report(period, type=["weekly","on_demand"], themes, evidence) — DRAFT (always created with status "Draft")
- send_slack_dm(summary, report_url) — SEND (the recipient is fixed to a pre-configured user; Juno can't choose who to send to)

**Deliberate omissions**

No create_jira_ticket(). Turning a signal into backlog work is a prioritization decision, and that's the PM's job. If Juno could file tickets, its clustering mistakes would become sprint commitments. In the prototype, a ticket is only created when user clicks the button.

No post_to_channel(), and no choosing who receives a DM. The report contains raw customer quotes and renewal risks. If an unchecked theme like "Halcyon renewal blocked" reached #product-squad or a CSM's DM, it would cause alarm based on something no one has verified. Juno sends only to pre-configured user and the user decides what gets shared.

No edit_report() or update_baseline() for past reports. Past reports are the baseline. If Juno could rewrite last week, it could quietly "fix" a comparison to match this week, and no comparison could be trusted.

No update_account_segment(). Juno can only look up segments, not change them. If it could reassign an account's segment, it could create its own "new segment" signals.

No write access to Jira, Slack or Notion sources (no comment, react, edit or delete). Juno is an observer. Even a harmless reaction on a customer thread tells the team they're being analysed, and that changes what people post.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

On-demand synthesis: starts when the pre-configured user asks, with pasted signals or a time period. Same ceiling (25 turns, 150 tool calls). Periods longer than 30 days need the user's confirmation first, because cost and run time grow with the volume of signals. The quote and unthemed-signal escalation rules apply. The "more than 10 changed themes" rule doesn't, because on-demand runs don't compare with a baseline.

Weekly Flow (one pass per weekly batch): collect the week's signals → group into themes → match to last week's themes → label with compute_theme_labels → check quotes with verify_quote → write the Notion draft → send the Slack DM.

Ceiling: 25 model turns and 150 tool calls per run. A normal week (~350 items, ~6 changed themes) needs about 12 turns and about 80 calls. The ceiling gives roughly double that headroom. If Juno hits it, it publishes only the themes that already passed verification, with the banner "Partial report: limit reached", and lists what it didn't finish. It never cuts the report short without saying so.

Escalate (no report published; Juno DMs pre-configured user the reason) when:
- 2 consecutive failed calls to Jira, the segment table or the baseline. Without these the comparison is wrong, not just less complete (see 01 · Context).
- More than 10 themes are labelled as changed. RocketShip usually has 3–7 changes a week.  If "everything changed", the grouping probably broke; the product didn't suddenly change.
More than 25% of the week's signals don't fit any theme. The grouping missed too much for the comparison to mean anything.
More than 30% of quotes fail verify_quote. The model is paraphrasing or inventing evidence, and that breaks the 30-second check.

Not an escalation: a week with 0 changes. "Nothing moved" is a valid result, and Juno reports it as one.

**Latency and cost target**

On-demand: results in under 5 minutes for a period of up to 7 days. Same $5 ceiling per request. If the estimate is higher, Juno asks the user to narrow the period before running.

Weekly flow: the run starts Monday at 06:00 and the Notion draft is ready by 07:00 (under 60 minutes, almost every week). The Slack DM goes out at 07:15. If the run isn't finished by 07:10, pre-configured user gets a DM saying "Report delayed" instead of silence. There's no target in seconds, because the run happens before anyone is at work. What matters is that it's ready before sprint planning.  Cost ceiling $5 per weekly run, about $20/month per PM. Costs stay flat because Juno compares against last week's summary, not all past raw signals.

## 04 Memory · Data Requirements

**What persists, at what scope**

- On-demand synthesis: nothing is kept between requests. Each run starts fresh from what's given: specific signals, or a time period for Juno to search in Jira, Slack and Notion. It can read previous synthesis reports, both drafts and published, as context.

- Weekly report: scoped to the product team (RocketShip). Juno must check the previous weekly reports in Notion to compare this week with last. It saves only the theme list (name, count, segments, accounts, quote links), not the raw signals, which stay in their source tools. Drafts can be read as context, but only reviewed reports count as the baseline for "what changed", so an unchecked mistake isn't carried into next week.

**Expiry and write rules**

Weekly themes are used as the baseline for 6 weeks, then archived. On-demand syntheses are not kept unless saved as a Notion report. Human corrections always win and never expire. Juno's original version is kept alongside them, marked as replaced. Juno never edits a past report.

## 05 Permissions · AI Risks & Mitigations

**The permission tier**

| Side-effect class | Tier |
|---|---|
| read | auto |
| draft | auto |
| write | confirm |
| send | auto |

**Justification**

Read · auto. Blast radius: none outside Juno. Nothing is changed or shared. The privacy risk is limited by scope: only the approved Slack channels, the SUP and RS projects in Jira, and the 3 Notion databases. No DMs or private channels.

Draft · auto. Blast radius: one person. The Notion report is created with status "Draft" and is visible only to the pre-configured user. Fully recoverable: it can be edited or deleted, and nothing reaches the team until the user shares it.

Send · auto, recipient fixed. Blast radius: one person, the pre-configured user, who reviews the report anyway. A Slack DM can't be unsent, which is why the recipient is set in configuration and Juno can't change it. Confirming a message to yourself would add friction with no safety gain.

Write · confirm. Juno has no write tools in v1: no Jira tickets, no edits to sources or past reports. Any future write (e.g. creating a Jira ticket from a theme) affects the team's backlog and is hard to undo quietly, so it needs the user's click every time.

## 06 Verification · AI Testing & Measurement

**The check before output ships**

- Quotes are real: verify_quote checks that every quote matches its source word for word.
- Duplicates: a code check makes sure the same issue from the same account in a ticket and a Slack thread is counted once.
- Labels: new, growing, fading and new segment come from fixed numeric rules applied to the counts, not from the model's judgement. compute_theme_labels recalculates each label and confirms it matches the rule.
- Coverage is complete: a code check confirms every source was read and no more than 25% of signals are unthemed.

**Failure behaviour**

- Quote fails: it's removed, and the theme shows "1 quote removed: not found in source". If a theme is left with fewer than 2 verified quotes, it's marked "Low confidence: needs review".
- Possible duplicate: counted once and marked "Possible duplicate". Juno undercounts rather than inflates.
- Label doesn't match the rule: the rule's label wins, and the theme is marked for review.
- Coverage fails: the report shows a banner naming the missing source, and affected themes show "Not comparable this week" instead of fading.
